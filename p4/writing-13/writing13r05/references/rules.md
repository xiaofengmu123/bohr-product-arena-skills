# 规则：基金申请书写作的四问、七要素与证据溯源

本文件是执行时的硬规则，与 `SKILL.md`、`checklist.md` 配套。所有"该不该这么写"的判断都回到这里与材料证据，不凭感觉、不写套话。

## 1. 四问 → 可观察判据（质量增益的来源）

题目四个关键词必须翻译成"可逐句核验"的判据，而不是泛泛要求"准确、完整"。

### 1.1 立得住（立项依据）
- 每段必要性论证必须同时出现四项，缺一即视为未立住：
  1. 现状到哪一步（引用具体已有工作或数据，带 locator）；
  2. 关键瓶颈是什么（一句话可复述，非口号）；
  3. 申请人的前期观察/证据（来自材料，带 locator + quote）；
  4. 为什么现在必须做（时间紧迫性 + 技术窗口，来自材料）。
- 禁令：把研究意义写成政策口号堆叠；无来源的"重大意义""迫切需求"一律标 `unmapped` 或删除。

### 1.2 说得准（创新点）
- 每条创新点必须指名"具体已有工作 + 差异 + 为什么难 + 凭什么做得成"：
  - 已有工作：作者/年份/方法名（若材料只有一篇，不得虚构其他对照）；
  - 差异：一句可证伪的对比陈述；
  - 为什么难：来自材料中的技术瓶颈；
  - 凭什么做得成：前期成果或平台条件证据。
- 禁用无法核验的修饰："首次""国际领先""填补空白""重大突破"。出现即改写为可核验的具体差异，并在 `change_log` 记录改写动作。

### 1.3 对得上（目标—内容—路线—指标一致性）
- 建立四级对应表（见 `proposal_draft.md` §8），行结构固定为：
  `研究目标 | 研究内容 | 技术路线步骤 | 考核指标 | 证据 locator`。
- 硬校验（`scripts/main.py check` 会复核）：
  - 每个研究目标 ≥ 1 条研究内容、≥ 1 条技术路线步骤、≥ 1 个可考核指标；
  - 数量必须对等：目标三个 → 内容三条 → 路线三条 → 指标三套；不出现"目标三个、路线两条、指标另说一套"。
- 指标必须是可考核量（数值、判定标准、观测现象），不允许"达到国际先进水平"这类空指标。

### 1.4 查得到（引用 / 数据 / 前期成果 / 政策口径溯源）
- 每个数字、术语、引用、图表、关键论断都要有 `source_ref` + `locator` + 逐字 `quote`。
- 严格区分"已完成"与"拟开展"：
  - 已完成：材料中有对应前期成果/数据，quote 取自材料；
  - 拟开展：材料无对应证据，标注 `planned`，进 `pending_human`，不得写成已完成。
- 政策口径（如有）同样要溯源，不引用题面未出现的政策原文。

## 2. 七要素（默认集，可被运行时覆盖）

默认七个要素：**立项依据、科学问题、研究目标、研究内容、技术路线、创新点、研究基础与可行性**。

- 每要素必须产出"可直接进入申请书的章节稿"（非提纲、非建议、非整篇空模板套用）。
- 若 `case.json` 或 `organizer-workorder.json` 给出不同要素清单，以题面为最高优先级，覆盖本默认集，并把差异写入 `version_boundary`。
- 每要素下的段落要与 `fact_source_map` 的 `element` 字段一一对应，形成"段落—要素—证据"三级对应。

## 3. 事实台账与三级对应

`fact_source_map` 每条记录至少含：

| 字段 | 含义 | 要求 |
|---|---|---|
| `claim` | 关键论断/数字/术语 | 一句话可复述 |
| `element` | 所属七要素 | 非空，用于三级对应 |
| `kind` | 类型（number/term/citation/figure/claim/policy） | 非空 |
| `source_ref` | 来源文件 | 文件:页 或 文件 |
| `locator` | 段/表/图定位 | 非空 |
| `quote` | 逐字引文 | 非空，逐字、不意译 |
| `status` | mapped / unmapped / conflict | mapped 必须有 locator+quote |
| `note` | 备注（含已完成/拟开展标记） | 可选 |

- `unmapped`：材料中找不到来源的论断，逐条进 `uncertainty`，不得伪装成有来源。
- `conflict`：同一指标两个来源不一致时，两个都记，标 `source_conflict`，双方依据都写进 `version_boundary.anomalies`，不擅自选一。

## 4. 不编造红线

- 不新增材料外事实：稿件中出现的数字、人名、文献、成果、政策口径必须能在材料中找到逐字依据。
- 不虚构引用、DOI、卷期页码、图表内容；缺失即写 `not_reported` 或进 `pending_human`。
- 不把 `in_progress`/`partial` 改成 `done`；材料不足就 `partial` 或 `insufficient_evidence`。
- 不预写正式测试答案/白板；平台提供所有对照。

## 5. 冲突与复现规则

- 同一事实两个来源冲突 → 两个都记录，标 `source_conflict`，在 `version_boundary.anomalies` 写明双方依据，不擅自选一、不擅自改分/改数。
- 材料超长 → 分段读取，记录已读范围；未读部分进 `version_boundary.material_gaps`，不得声称已全部核对。
- 重复运行要求结果一致：台账、快照、change_log 全部落盘，脚本无随机性（无随机种子依赖），同一输入两次运行产出一致的 `result.json` 结构。

## 6. 版本与边界字段

`version_boundary` 四个子字段：

- `modification_diff`：对原文的修改差异（改了什么、为什么改、改前/改后）；
- `manual_confirm`：需人工确认项（数字、政策口径、已完成/拟开展归属等）；
- `material_gaps`：材料缺口（未提供、超长未读、乱码、缺页）；
- `anomalies`：异常（来源冲突、模型拒答、编码损坏、格式错乱）。
