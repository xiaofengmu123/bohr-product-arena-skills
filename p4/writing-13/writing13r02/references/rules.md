# 基金申请书写作规则与证据溯源规范

本文件是 `SKILL.md` 的补充规范。执行写作任务时逐条遵守；与 `case.json` / `organizer-workorder.json` 冲突时以题目契约为准。

## 1. 七个要素（默认定义，可按题目契约覆盖）

基金申请书七要素及其可观察完成标准：

| 要素 | 完成标准（可观察、可操作） |
|---|---|
| 立项依据 | 用材料中的领域现状与关键瓶颈说明"别人做到哪一步、还差什么、为什么是我们"；不以政策口号堆叠充当研究意义 |
| 科学问题 | 把宽泛兴趣收敛为可回答、可分解、有边界的问题；与研究方法不脱节 |
| 研究目标 | 数量适度、层次清楚、可考核；每个目标附可测指标 |
| 研究内容 | 与目标一一对应，逐条可执行，不另起一套 |
| 技术路线 | 按研究内容组织步骤、方法与关键节点；写清输入输出、可行性依据、风险与备选方案，不罗列方法名 |
| 创新点 | 在梳理代表性已有工作的基础上定位差异；写清新在哪、为什么难、凭什么做得成 |
| 研究基础与可行性 | 把前期成果、平台条件、团队分工组织成"能力—证据—与本研究的关系"证据链 |

若 `organizer-workorder.json` 给出七要素定义，以其为准并记录在 `version_boundary.modification_diff`。

## 2. 四问质量门（立得住 / 说得准 / 对得上 / 查得到）

每段正文落笔前先过四问：

1. **立得住**：本段是否回答了"为什么值得做、为什么现在做"？证据是否指向材料中的具体瓶颈，而非口号？
2. **说得准**：创新点是否写明了与具体已有工作的差别？是否出现"首次 / 国际领先 / 填补空白"等无法核验的修饰且未附出处？
3. **对得上**：目标、内容、路线、指标是否一一对应（写入 `consistency_matrix`）？不得目标三个、路线两条、指标另说一套。
4. **查得到**：每个数字、术语、引用、图表、论断、政策口径是否可回溯到材料 `locator + quote`？是否区分已完成与拟开展？

## 3. 事实-来源映射（fact_source_map）

每条事实记录必须包含：

- `claim`：正文中实际写出的论断（与产物逐字一致）
- `kind`：`number | term | citation | figure | assertion | policy | data`
- `source_ref`：来源文件（相对路径）
- `locator`：页码 / 段落 / 表图定位
- `quote`：材料中的逐字原文（不得转述，不得省略关键限定词）
- `tense`：`completed`（已完成 / 前期成果）/ `planned`（拟开展）/ `external`（外部文献或他人成果）/ `n/a`
- `status`：`mapped`（有据）/ `unmapped`（缺证据）/ `conflict`（多源冲突）
- `confidence`：`high | medium | low`

要求：

- `mapped` 事实必须同时有 `source_ref + locator + quote`，否则只能降为 `unmapped`。
- 冲突不隐藏：同一指标两个来源不一致时两条都记，标 `conflict`，并写入 `version_boundary.anomalies`，不擅自选一。
- 已完成与拟开展必须显式区分，写错 tense 视同事实性错误。

## 4. 一致性矩阵（consistency_matrix）

构建"目标 ↔ 内容 ↔ 路线 ↔ 指标"对应表，每条形如：

```json
{"goal": "目标1…", "content": "内容1…", "route": "路线步骤…",
 "metric": "考核指标…", "status": "aligned | missing | conflict", "note": ""}
```

- 目标、内容、路线、指标数量不一致时，`missing` / `conflict` 必须记录，并在正文修订或 `pending_human` 标注。
- 该矩阵直接服务于评分维度"结果正确性 / 结果完整性 / 质量增益"，是本章稿区别于"写作建议 / 提纲"的关键产物。

## 5. 不编造红线

- 不补造材料中不存在的数字、数据、DOI、卷期页码、实验结论、引用条目或运行结果。
- 不把文件名 / 领域标签当作事实；必须读实际文件内容。
- 不把未完成的 `partial` / `in_progress` 改写成 `done`。
- 无法核验的修饰词（首次、国际领先、填补空白等）不得出现在正文，除非逐字引证到具体来源，否则删除或降级为可核验表述。
- 示例（demo）输出必须显式标注"示例"，不得冒充正式案例结果。

## 6. 已完成 vs 拟开展

- 前期成果、已发表工作、已获数据 → `completed`，只能写材料中确有的事实。
- 研究方案、预期产出、待验证假设 → `planned`，措辞用"拟 / 计划 / 预期"，不得写成既成事实。
- 材料缺失的申请人证据 → 标 `pending_human`，正文用"（据材料可得的）"或留白并标注，不代作者补写。

## 7. 冲突与复现

- 冲突、分歧、材料缺口全部进 `version_boundary` 与 `uncertainty`，第三方应能据此重算同一结论。
- 重复运行结果应可解释一致：相同输入、相同材料、相同契约 → 相同结论；随机性操作固定种子或采用确定性布局。
- 变更只做增量：先落盘骨架，此后每次修改追加 `change_log`（时间 / 动作 / 原因 / 影响），不推倒重写。
