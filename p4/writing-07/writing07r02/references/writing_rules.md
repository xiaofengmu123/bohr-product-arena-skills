# 写作与证据规则细则

本文是 SKILL.md §5 的展开：四段组织、证据绑定、引用、冲突处理、变更记录与时间纪律的具体执行规则。正文写作由 Agent 完成，本文是 Agent 在每个阶段必须遵守的硬规则。

## 1. 四段组织与承接

### 1.1 研究背景（立得住）

- 落点：真实研究脉络 + 具体未解决问题或技术瓶颈，交代“为什么现在值得做”。
- 每句事实挂 `[S#]`；结论性判断若为作者推断，标注“作者判断”。
- 禁忌：空转铺垫（“近年来受到广泛关注”）、与本文无关的泛化重要性叙述、无来源的领域断言。
- 证据要求：背景中的数字、术语、技术约束必须有 locator + 逐字 quote。

### 1.2 相关工作（分得清）

- 先定**分组维度**：问题设定、方法路线、数据与评价方式，再按维度归组。
- **组内**：在同一维度上比较各工作的取舍、适用条件与局限，不用时间顺序罗列。
- **组间**：说明本工作相对各组的定位与差异。
- 每个工作条目至少含：问题设定、方法、数据与评价方式、结论、适用条件/局限、来源。
- 转述保留原文结论强度，不把“初步表明”写成“证实”。

### 1.3 研究空白（说得实）

- 空白只由三类证据推出：已引工作的共同限制、未覆盖场景、相互冲突的结论。
- 每处空白写明本文工作如何填补，并给出对应关系（空白 → 本文方法/实验）。
- 无法由文献推出的判断，显式标注“作者判断”，并写进 `uncertainty`。

### 1.4 贡献（对得上）

- 每条贡献是“方法/实验/结论”压缩成的可核对条目。
- 每条贡献映射到正文中的方法小节、图表编号或实验结果（贡献 → 证据位置）。
- 不夸大适用范围；适用范围以材料中的数据集/条件/指标为准。

## 2. 证据绑定规范

- 每个事实句（数字、术语、引用、图表、关键论断）末尾挂 `[S#]`，`S#` 全稿唯一。
- `evidence_map.json` 全稿一份，形如：

```json
{
  "S1": {"locator": "materials/paper.md#p3", "quote": "逐字片段", "kind": "fact"},
  "S2": {"locator": "materials/paper.md#p5", "quote": "We report X = 3.14.", "kind": "number"}
}
```

- `quote` 是材料中的**逐字片段**，不重写、不改数字；`locator` 指向段落/行/页码。
- `kind` 取值建议：`fact`（事实）、`number`（数值/单位）、`claim`（论断）、`citation`（引用）、`figure`（图表）、`method`（方法）。
- 数字、单位、统计量逐字复用；材料没有的不补，写 `MATERIAL GAP` 或 `not_reported`。

### 2.1 逐字 quote 选取规则

- 优先截取包含该论断的最小完整句或短语，不跨段拼贴。
- 省略号 `[…]` 只用于中段省略，且不得改变原意；首尾不省略。
- 若原句含错别字或明显笔误，逐字保留并在 `uncertainty` 说明，不擅自改字。

## 3. 事实池工作稿（work/facts.md）

逐份材料摘录到 `work/facts.md`，每条一行，格式：

```
[S#] | locator | kind | quote(逐字) | 用途(背景/相关/空白/贡献/引用)
```

- 摘录时只做搬运，不评判、不改写。
- 冲突信息两条都记，见 §5。
- 相关工作行额外标注所属分组与比较维度，供起草时按组归并。

## 4. 引用与元数据

- 引用只用材料中真实出现的来源；元数据（作者/年份/DOI/卷期页）缺失写 `pending_human`，不编造。
- 引用格式以案例指定为准；未指定时用作者—年份，并在 `uncertainty` 声明该假设。
- 覆盖三类工作：关键工作、代表性工作、近期进展；每条引用落在具体论断上，论断与引用一一对应。
- 引用元数据逐条核对：作者拼写、年份、标题、期刊/会议、卷期页，材料里没有的字段留 `not_reported`。

## 5. 来源冲突与不确定

- 同一指标两个来源不一致：两条都记录，标 `source_conflict`，在 `uncertainty` 说明取舍依据或待人工确认。
- `sources` 中冲突项 `kind` 追加 `source_conflict` 标记；`uncertainty` 写 `{item, reason}`。
- 材料不足、未证实、需人工确认处：写 `uncertainty` 或 `pending_human`，宁可标注不足，不用示例填充。

## 6. 变更记录与数值保全

- 每次组装/改写记 `{at, target, before, after, reason}`；`at` 用阶段标记（如 `P3-01`），`target` 指向稿件位置或 `[S#]`。
- `change_log.json` 与 `result.json.change_log` 同步；可回退到改写前文本。
- 数值与单位保全清单可并入 `preserved_facts.json`，每项：原值、改写后值、是否改动、理由。
- 数值改动默认不允许；确需调整（如单位换算）必须逐字记录换算依据，且换算结果可复核。

## 7. 时间预算与早落盘纪律

- 阶段预算见 SKILL.md §4；每阶段完成执行 `checkpoint --phase <KEY> --requests <N>` 记账。
- **P1 骨架是硬门槛**：先跑 `skeleton` 落盘 `result.json`(v0)，再进入写作；此后每次改进都覆盖写盘，任何时刻磁盘上都有一份合法 JSON。
- 超支：在 `limitations`/`pending_human` 说明；停止新增内容，优先保住已落盘检查点。
- 断点续跑：中断后先 `budget` 查看剩余预算，重读 `work/` 与 `output/`，从最近未完成阶段继续，不重读大 PDF。

## 8. 比较矩阵模板（分组比较用）

相关工作分组后，用下表在同一维度上比较（列名按案例调整）：

| 工作 | 问题设定 | 方法路线 | 数据与评价方式 | 结论 | 适用条件/局限 | 来源 |
|---|---|---|---|---|---|---|
| … | … | … | … | … | … | [S#] |

- 空单元格写 `not_reported`，不得从材料外补写。
- 组内比较结论（谁在什么条件下更优/更省/更稳）必须能从表中各行的“方法路线/数据与评价方式/结论”推出，否则标“作者判断”。

## 9. 确定性

- 结果不含随机成分；若必须采样/排序，用固定种子或字典序。
- `runtime` 是唯一允许的运行期测量字段；`change_log.at` 用阶段标记而非墙钟时间。
- 同一输入两次运行产物的结构与事实内容一致。
